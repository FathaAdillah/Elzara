## 1. Ruang lingkup dan batas kepercayaan (trust boundaries)

### 1.1 Yang ada di dalam lingkup

Tiga deployment mandiri pada satu VPS + Docker Compose, **satu node, tanpa klaim HA** (Doc 11 B-15; Doc 01 §11, §14):

| Aplikasi | Stack | Peran keamanan |
|---|---|---|
| `api` | Laravel (PHP 8.4) + PostgreSQL 16 + Redis 7 + Horizon | satu-satunya pemegang kebenaran: uang, stok, kuota, otorisasi |
| `admin` | Next.js (TypeScript) | permukaan operator; cookie sesi terpisah (`elzara_admin_session`, guard `admin`); SSR meneruskan cookie yang sama — bukan BFF pemegang sesi (ADR-007 (BFF/sesi) Bentuk C) |
| `web` | Next.js (TypeScript) | permukaan publik; SSR/ISR; tidak memegang secret; cookie `elzara_web_session`, guard `web` |
| Datastores | PostgreSQL, Redis, Elasticsearch, MinIO (6 bucket) | tidak boleh terekspos internet (Doc 01 §11.1) |
| Pihak luar | payment gateway, kurir, provider WhatsApp, Cloudflare, registry image, CI, provider sosial (Google/X) | semua masuk lewat adapter + signature; identitas sosial hanya lewat email terverifikasi (T-39) |
| Manusia | customer, operator dengan 10 role admin, dev/ops, klien | laptop operator = permukaan nyata (kode klaim + bukti pembelian) |

Cakupan bisnis tiga jalur: Ready to Ship, Pre-order/Group Order (deposit → pelunasan → barang tiba → kirim), Request Order (kuotasi privat per akun), plus jalur **MarketplacePurchase** — pembelian atas nama buyer di marketplace pihak ketiga (Doc 11 B-4: modul `MarketplacePurchase`, tabel `marketplace_purchases` / `claim_codes` / `proof_files`; di balik feature flag `procurement_lane`, default mati).

Di luar lingkup: keamanan fisik VPS/data center, kepatuhan PCI penuh (diperkecil dengan hosted gateway, Blueprint §13), multi-tenant/multi-vendor (Doc 01 §1.2).

## 3. Matriks ancaman

Legenda `sisa risiko`: **T** = masih terbuka penuh · **S** = terkurangi oleh desain, tapi belum diuji · **B** = diblokir constraint/mekanisme DB (pertahanan akhir, Blueprint §6).
Tindakan yang membawa `⚑` tidak bisa ditutup tim dev sendiri — lihat §6.

**Mekanisme auth/sesi yang menjadi dasar baris T-01…T-09 dan T-39…T-41 sudah diputus pemilik 2026-11-18** (register mengikat Doc 11 §4.4 A–C/I; ADR-007 (BFF/sesi) amandemen; ADR-012 (RBAC/identitas/dependensi); rincian Doc 01 §9.4): Sanctum `statefulApi` cookie same-site karena edge satu host dengan pemisah path; guard `web`/`admin` dengan cookie `elzara_web_session`/`elzara_admin_session` (`Secure; HttpOnly; SameSite=Lax; Path=/`); CSRF wajib semua mutasi (`XSRF-TOKEN` sengaja JS-readable, `sanctum/csrf-cookie` dipanggil dulu); login admin email+password + `is_operator = true` + `status = active` + 2FA wajib, tanpa jalur sosial; RBAC admin spatie granular per aksi + pemberian langsung ke user + `role_scopes`; bypass `is_admin` hanya di guard admin dan setiap pemakaian wajib menulis `audit_logs` (`rbac.bypass` + `reason` + `request_id`); storefront hybrid (email+password, Google, X) untuk login dan registrasi, penggabungan akun hanya lewat email terverifikasi; tanpa PAT/bearer di browser, tanpa rahasia di `NEXT_PUBLIC_*`; rate limit login/OTP/reset di edge + `RateLimiter` API; `X-Actor-Type` = `web | admin | system` diisi server dari guard. Persetujuan atas kontrol sesi tercatat di §6, bersama status bukti tertulis.

| id | ancaman | aktor | permukaan serangan | kontrol saat ini | sisa risiko | tindakan |
|---|---|---|---|---|---|---|
| T-01 | **Credential stuffing & abuse OTP** pada login customer & operator | bot terdistribusi; pemegang daftar kredensial bocor | `POST` login (email `citext` unik), endpoint OTP/WhatsApp, reset password | `[desain]` password hashing supported + rate limit login/OTP/reset di **edge DAN API** (`Illuminate\Support\Facades\RateLimiter`, bukan paket composer — Doc 01 §9.4, ADR-007 (BFF/sesi) D-5a); lockout per akun dengan backoff; bot protection (Blueprint §13); **2FA wajib untuk login admin** (`is_operator` + `staff_2fa_secrets`, Doc 11 §4.4 A) | **T** — throttle per-IP kalah oleh botnet; tidak ada pemeriksaan "kredensial ini pernah bocor"; akun storefront tanpa MFA bila klien tidak mewajibkan | (a) throttle bertahap per **akun** dengan backoff + lockout berbukti; (b) MFA untuk akun **storefront** tetap keputusan klien ⚑ (login admin sudah wajib 2FA); (c) ambang alert rasio 401/login per menit per IP+akun; (d) email terverifikasi sebagai syarat checkout |
| T-02 | **Session hijacking / fixation & pencurian token** | XSS-bot, orang satu jaringan, stolen laptop | cookie sesi, Redis sesi, admin session | `[desain]` dua cookie terpisah `elzara_web_session`/`elzara_admin_session`, keduanya `Secure`+`HttpOnly`+`SameSite=Lax`+`Path=/` (Doc 01 §9.4 ← ADR-007 (BFF/sesi) D-2a); guard `web`/`admin` terpisah — **cookie storefront tidak pernah diterima guard admin, jadi XSS storefront bukan akses admin**; `SESSION_DRIVER=redis`; **tidak ada token jangka panjang di browser**: `personal_access_tokens` tidak dibuat, tidak ada bearer di JavaScript/localStorage, tidak ada rahasia di `NEXT_PUBLIC_*` (ADR-007 D-3a/D-4); same-site karena edge satu host, tanpa CORS lintas origin (Doc 01 §2.6) | **T** — belum ada aturan regenerasi session id saat login/naik hak akses yang teruji; tidak ada jalur **pencabutan sesi massal** yang jadi prasyarat runbook `data-breach.md`; HttpOnly tidak menghentikan XSS yang membaca data lewat DOM | (a) regenerate session id saat login, perubahan role/permission, dan perubahan password; (b) prefix `__Host-` untuk cookie admin (kompatibel dengan `Path=/` + `Secure` + tanpa `Domain`); (c) endpoint `POST /auth/sessions/revoke-all` + perintah artisan; (d) TTL sesi pendek untuk admin; (e) test: cookie guard `web` ditolak guard `admin`; (f) mekanisme sudah diputus — sign-off Fatharoni tercatat di chat bot Product Engineer pada 2026-11-22, dengan persetujuan klien dikonfirmasi pemilik (threat model §6); Q-2 terjawab oleh pemilik proyek pada 2026-11-22: klien tidak punya IdP/SSO sendiri, tidak ada provider OIDC ⚑ (§6) |
| T-03 | **CSRF** pada mutasi | halaman musuh di browser yang sudah login | semua mutasi non-GET API & form | `[desain]` **CSRF wajib pada semua mutasi, tanpa pengecualian untuk admin** (ADR-007 (BFF/sesi) D-2a); cookie `SameSite=Lax` + nama cookie/guard terpisah; `XSRF-TOKEN` sengaja tidak HttpOnly karena dibaca JS untuk header `X-XSRF-TOKEN` (desain Sanctum, bukan kelalaian); klien memanggil `sanctum/csrf-cookie` sebelum mutasi pertama; same-site → tanpa konfigurasi CORS lintas origin (Doc 01 §2.6, §9.4); mutasi finansial wajib `Idempotency-Key` (Blueprint §7) | **S** — `Lax` mengizinkan navigasi top-level GET; API-first `/api/v1` bisa dipanggil dari klien non-browser; belum ada matriks route→CSRF yang diuji | (a) test matriks "setiap route mutasi menolak request tanpa token"; (b) validasi `Origin`/`Sec-Fetch-Site` allowlist; (c) mutasi tidak pernah di GET; (d) dokumentasikan di kontrak API (Doc 12 §3) |
| T-04 | **Clickjacking** (framing halaman checkout/admin) | halaman phising | iframe di halaman pihak ketiga | `[desain]` `X-Frame-Options: DENY` + CSP `frame-ancestors 'none'` sebagai baseline edge sejak Sprint 0 (Doc 01 §9.3, Doc 08 §6) | **S** — alur gateway pembayaran bisa butuh frame/redirect → godaan melemahkan header secara global, bukan per rute | (a) header test otomatis di **semua** route HTML (staging); (b) allowlist eksplisit per rute untuk embedded gateway; (c) jangan pernah melepas `frame-ancestors` di `admin` |
| T-05 | **XSS stored lewat ulasan produk (UGC)** | customer dengan order selesai; akun hasil T-01 | `POST /reviews`, lampiran ulasan, halaman PDP publik, dashboard moderasi | `[desain]` ulasan terkunci pada order selesai + termoderasi (Doc 01 §3.4 D6); "jangan pernah render HTML dari konten user tanpa sanitizer" + escaping (Doc 01 §9.3); antrean moderasi `admin` (Doc 06 §3.9) | **S** — belum diputus ulasan boleh markup apa; reviewer admin melihat teks mentah di dashboard = XSS **ke staff**, bukan ke publik | (a) kebijakan teks-datar (`nl2br` + escaping), tanpa HTML; (b) kalau rich text: sanitizer allowlist + test; (c) redam konten di UI admin (`contenteditable=no`, `textContent`) — jangan render apa yang ditulis publik ke staff; (d) moderasi wajib sebelum tayang, catat di `review_moderation` |

## 4. Batas yang kita **tidak** langgar (spoofing, anonimitas, dan perilaku observasi)

Bagian ini ada di threat model — bukan di halaman "values" — karena melanggar batas ini adalah **risiko hukum bagi klien**, bukan sekadar kelalaian teknis (Doc 11 §2 menetapkan batas KI sebagai hal yang tidak diubah Blueprint; Doc 08 §1 mencatat bukti mentah disimpan di luar repo).

**Yang tidak kita lakukan:**

1. **Tidak scraping massal, tidak menyalin.** Yang diambil dari situs referensi hanya kategori fitur (Doc 05) dan fakta struktural — nama rute, kode status, nama file chunk, header respons, jumlah item (Doc 08 §1). Tidak ada kalimat marketing, deskripsi produk, foto, ikon, logo, font, CSS, atau baris kode pihak lain yang masuk ke repo (Doc 01 §15; Doc 08 §1).
2. **Tidak memakai kredensial yang bukan milik pemilik proyek.** Peninjauan area login hanya pada **akun customer milik pemilik proyek, dengan izinnya**, dan hanya-baca: tanpa membuat order, tanpa transaksi pembayaran, tanpa mengubah/menghapus data, tanpa upaya masuk ke panel admin sistem pihak lain (Doc 00 §Metode observasi, §Batas pekerjaan). Tidak ada upaya eskalasi hak akses ke sistem pihak lain.
3. **Tidak menyimpan data pribadi customer pihak ketiga** sebagai "bahan referensi". Yang dicatat hanya kategori fitur dan jenis field (Doc 00 §Batas). Di platform kita sendiri, `buyer_account_ref` jalur MarketplacePurchase disamarkan dan **bukan** kredensial (Doc 09 §Procurement).
4. **Tidak membuat/mengirim konten spoofing.** Tidak ada phishing, tidak ada impersonation brand pihak lain, tidak ada screenshot situs orang lain sebagai aset. Seeder demo berisi 10 produk fiktif **buatan sendiri** dengan nama karakter/IP tak terdaftar dan gambar SVG orisinal berlisensi bebas (Doc 10 §8).
5. **Menghormati sinyal mesin situs sumber.** `robots.txt` mereka memasang `Content-Signal: ai-train=no, use=reference` dan memblokir crawler AI; penghormatan sinyal itu bagian dari metode dan bagian dari bahan bicara ke klien (Doc 00 §Metode observasi).
6. **Blueprint dipakai sebagai resep, bukan sebagai klaim realitas.** Disclaimer Blueprint sendiri: "Struktur internal Snowe GO tidak diverifikasi"; hasil observasi kita (Doc 08) justru memverifikasi situs sumber **tidak** berjalan pada topologi tiga aplikasi API-first yang digambar Blueprint §3. Setiap kalimat di dokumen mana pun yang berbunyi "situs sumber memakai arsitektur ini" **salah dan harus dihapus** (Doc 11 K-4).
7. **Kredensial klien tidak dibagikan di chat**; bila nanti perlu akses akun milik klien sendiri (gateway/kurir/panel), dipakai environment variable + **akun khusus proyek**, bukan kredensial pribadi (Doc 00 §Batas; T-26).

**Konsekuensi bila batas ini dilanggar:** tuntutan dari pemilik merek/konten, penghentian layanan hosting/payment oleh provider, hilangnya kepercayaan klien, dan ditemukannya kembali oleh pemilik situs sumber lewat jejak yang sama (header, fingerprint aset). Semua itu bukan "cosmetic risk"; karena itu T-35 diperlakukan sebagai entri ancaman, bukan catatan etika.

## 7. Catatan penegakan (agar dokumen ini tidak jadi wish list)

**Verifikasi Sprint 0 (2026-11-22):** [register kontrol-ke-tes](threat-model-verification.md) memetakan seluruh T-01…T-42 dan kontrol lintas bagian ke asersi yang tersedia, perintah dan gap. Inspeksi bukan hasil eksekusi suite baru; tidak menutup semua kontrol desain atau gerbang staging.

1. **Satu baris = satu penanggung jawab.** Tiap `tindakan` ditagih ke tiket/ADR dengan owner peran (`superadmin`, `penanggung jawab rilis`, klien). Tidak ada tindakan tanpa tiket.
2. **Kontrol dianggap ada hanya kalau test-nya ada.** Gerbang yang sudah tertulis: CI C1–C8 (Doc 10 §10), matriks otorisasi server-side per role, suite concurrency PostgreSQL via Testcontainers, dua sasaran test paralel Blueprint §16 (1.000 checkout / 500 kuota) yang dijalankan k6, Playwright untuk tiga alur (Doc 01 §13). Baris T-n yang test-nya belum ada ditandai `⚑` atau tetap `S`/`T`.
3. **Jangan mengarang kontrol.** Kolom `kontrol saat ini` hanya berisi sesuatu yang **diperintahkan oleh Blueprint §13/§14 atau Doc 01 §9 / Doc 10** — status implementasi harus dibaca per kontrol di register verifikasi, bukan disimpulkan dari baseline desain.
4. **Perubahan dokumen induk wajib menyegarkan tabel ini.** Nama tabel/role mengikuti **Doc 11 §4** (daftar rename resmi), **§4.4** (keputusan pemilik 2026-11-18: identitas/RBAC/dependensi), dan **B-10**, bukan draft Doc 01/00 yang sedang ditulis ulang paralel. Untuk tiga daftar lain yang dulu tertulis berbeda antar dokumen, pemiliknya tunggal dan dokumen ini hanya mengutip: **nilai status** = Doc 11 §8.3 dengan **CHECK Doc 09 sebagai pemegang nilai final** (kalau berbeda, Doc 09 yang menang dan baris di dokumen ini yang diperbaiki), **nama event** = Doc 11 §8.4 yang daftarnya hidup di **Doc 12 §6.2**, **nama antrian Horizon** = Doc 11 §8.1 (tujuh: `payments`, `orders`, `inventory`, `notifications`, `imports`, `reports`, `media`). Konsekuensi untuk tabel §3: `ParcelShipped`, `PoBatchArrived`, dan `RefundApproved` adalah nama mati — yang dipakai `PackageShipped`, `GoodsReceived`, dan `RefundCompleted`; dan `pending`, `draft` (di `order_status`), `customs` (di `fulfillment_status`), `shipped_by_supplier` bukan nilai kanonik di sumbu mana pun.
5. **Baseline ZAP, hasil drill restore, hasil load test, dan bukti bypass test** disimpan sebagai artefak di `docs/`/CI — "bukti, bukan niat" (Doc 10 §9).
